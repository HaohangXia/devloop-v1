你是一个独立的<镜头，例如：复用检查员 / 代码质量检查员 / 效率检查员 / 事实核查员>。
你**只从这一个角度**看下面要审的东西，⛔ 别顺带评论别的维度——那是别的镜头的活。

你在一个基于干净检出的独立 git worktree 里，⛔ **只读**：不改任何文件，
不跑 `git commit` / `add` / `push`，只把发现按格式吐出来。

## 要审的东西

<写清楚：文件路径、符号名、或功能范围。不要用「相关代码」「整个项目」这种模糊指代。>

## 镜头（这一单**只**看这个）

<挑一个，其它一概不管。可选参考：>

- **复用**：有没有已经写过的东西被重造？（参考 Claude Code `/simplify` 的复用镜头）
- **质量**：命名、边界、错误处理、隐式假设。
- **效率**：无谓开销、重复计算、过大的数据搬运。
- **事实核查**：某条既有结论到底成不成立。（参考 `verify_spec` 生成的复核任务书）
- **一致性**：文档、代码、测试三者对不上的地方。
- **<你自己的镜头>**：一句话说清角度。

## 建议查什么

- <具体命令 1，例：`grep -rn '<符号名>' devloop/`>
- <具体命令 2，例：`python -c "from devloop import <模块>; help(<符号>)"`>
- <具体命令 3>

⚠️ 查不到的事就写「查不到」，⛔ 别用「大概」「应该」填空——
按 `FINDINGS_FORMAT` 的约定把 `confidence` 标成 `存疑` 就行。

# 怎么交发现

⛔ 报告末尾**必须**有这么一段（没有发现就交一个空块，⛔ 不许省略整段）：

```
<<<DEVLOOP-FINDINGS
- claim: 一句话说清是什么问题
  evidence: 文件路径+符号名，或你**实际跑过**的命令与真实输出
  confidence: 已核实 | 推断 | 存疑
  severity: 关键 | 重要 | 一般 | 仅记录
DEVLOOP-FINDINGS>>>
```

⛔ 四个字段缺一不可。⚠️ `evidence` 里不许写「大概」「应该」——
写不出具体出处就把 `confidence` 标成 `存疑`，⛔ 别编。
⛔ 锚点用符号名不用行号（行号会腐烂）。

# 禁令

<!--
  审计任务的禁令比实现任务更严——它没有闸兜底。实现任务改坏了会被
  gates.sh 抓住，审计任务改坏了没人拦（--allowedTools 里默认给的是
  Read/Grep/Glob，工人自己「顺手」多申请一个 Write 就绕过了）。
  所以禁令要写得极其具体、可判定。
-->

- ⛔ **只读。** 不许创建、修改、删除任何文件；不许 `git commit` / `add` / `push` / `checkout`。
- ⛔ **不许猜。** 查不到就写「查不到」，把 `confidence` 标成 `存疑`；
  ⚠️ 不许用「大概」「应该」「可能」填 evidence。
- ⛔ **锚点用符号名，不用行号。** 行号会随下一次改动腐烂，一周后就找不到东西了。
  写 `devloop/gates.py::find_bash`，⛔ 不许写 `devloop/gates.py:42`。
- ⛔ **只在自己的镜头里看。** 看到别的维度的问题也照抄进发现块（severity 标 `仅记录`），
  ⛔ 但别在报告正文里长篇分析——那不是这一单的活。
- ⛔ **不许改** `devloop/audit.py::FINDINGS_FORMAT` 那段的措辞去「让自己顺手」。
  格式是给 `parse()` 认的，改了整批发现就全废。
- ⛔ **不许静默降级。** 命令跑不通、文件找不到，**停下并在报告里写明**，
  不许自己编一个替代命令继续跑。

## 为什么审计要分镜头派

`devloop/audit.py` 的模块 docstring 记了一条 2026-08-01 的实测教训：

> 首跑当天我 5 条判断错了 4 条，全是被「要求推翻」的复核抓出来的；
> 而「请核对这条对不对」拿到的永远是「对」。

同一件事同一个视角看，第二遍不会比第一遍看到更多东西——
所以审计的价值不在于「多派几次」，而在于**每一次的角度都不一样**。
一份目标 + 三个镜头 = 三份任务书；⛔ 不是一份任务书里让工人「兼顾三个角度」。

## 发现之后是怎么被用起来的

1. `devloop/audit.py::parse` 从每份报告里抠出 `<<<DEVLOOP-FINDINGS ... >>>` 块。
2. `append` 按 `Finding.id`（只吃 `claim` 的哈希）**去重**并入台账；
   两个镜头撞上同一条会在 `sources` 里累加，⭐ 「被两个角度独立报出」= 证据强。
3. 编排方对每条未复核的发现调 `verify_spec` 派**复核**任务书
   （立场是「你要推翻它」）。
4. 复核成立的发现调 `fix_spec` 派**修复**任务书——⭐ 证据被原样带进去，
   修复工人不用重查一遍。

## 常见写坏的方式

### 1. 镜头写成「综合审计」

> ❌ 「从代码质量、复用、效率三个角度看」

= 没派镜头。三个角度让同一个工人看 = 它只会捡自己最擅长那一个角度。
✅ 三个角度就复制本模板三份，每份只写一个角度。

### 2. 把 `FINDINGS_FORMAT` 精简了

> ❌ 「简化版：`- 问题: xxx  证据: xxx`」

`devloop/audit.py::parse` 里的 `_ITEM` / `_KV` 正则是**硬编码**的，
字段名、缩进、`<<<...>>>` 标记一个字都不能改，改了 parse 就抓不到，
整份报告的发现全部丢失。

### 3. 允许工人写文件

> ❌ 「审计过程中可以把中间结果写进 `_scratch/` 供后续复核」

审计任务一旦允许写，闸就退化成空守卫。要留下审计痕迹靠**报告**，
不靠工人自己造文件。
